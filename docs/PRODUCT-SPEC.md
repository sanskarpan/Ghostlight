# Ghostlight product behavior beyond the technical baseline

Normative revision 2. SPEC.md governs lifecycle/generation/cloud-side correctness, and this file extends SaaS, review, scheduling and fleet behavior. Organization/billing/identity follow shared SAAS-FOUNDATION.md. The roadmap defines when each capability is released.

## 1. Organization, projects and repository ownership — 1.0

Every customer-owned record has `organization_id`; child project/repository/environment relations use composite organization FKs and FORCE RLS. Platform catalog/signing/native discovery roles are explicitly separate. A trusted organization transaction wrapper resolves membership/key, sets local context and forbids cross-org reference insertion. Preview UUID unguessability is not authorization. Customer-owned repository names, costs, resource counts and evidence are not exposed through global dashboard aggregates.

Roles: owner, billing-admin, platform-admin, developer, reviewer, reliability-engineer and auditor. Project/environment ACL narrows organization role; developers cannot self-publish templates or grant cloud permissions. Reliability authors propose reviewed scenarios; experiment execution authority is separate where required. Service principals/API keys have scope, project binding, expiry and immutable audit. Customer owner is not a platform/cloud operator.

GitHub installation connection uses a server-stored expiring intent binding actor/organization/provider state. Callback verifies provider identity; fetch installation owner/repository grants through App APIs. Associate each installation/repository with a single customer authority by default; a separately reviewed organization transfer is needed to reassign it. Matching email/domain or a client-supplied installation ID is insufficient. User project access is not inferred solely from App installation; authorize membership/repository grants on every mutation.

Installation deletion/repository removal prevents new admission/reporting and revokes affected guest/runtime grants as policy requires. Independent native cleanup does not depend on GitHub access. Existing historical reports retain authorized provenance; they do not become public because a repo changes visibility.

## 2. Catalog, templates and qualification — 1.0/1.5

Project references services/owners and approved template versions. A template contains immutable recipe, role/dependency schema, fixture/profile, network edges, health/test contract and compatible module/runner digests. States `draft -> qualifying -> published -> deprecated -> retired`; publication needs independent create/update/gate/destroy evidence and authorized reviewer. Source PR cannot publish a privileged template. A revoked unsafe version blocks new admissions and schedules affected resources for reviewed migration or isolation.

Environment keeps exact template/module/version even when “latest” changes. Updating is a new generation with compatibility/permission/cost checks. Retiring a template does not remove runner/module needed to clean up old state. Additional workload support starts with one qualified recipe; generic catalog breadth is earned by qualification.

In 1.5, service topology is a bounded DAG (initial <=20 services/50 edges) with platform-owned dependency classes and explicit egress bindings. Cycles requiring synchronous startup or unrestricted connectivity are rejected or represented through a reviewed profile. Readiness progresses by declared dependencies; partial service failure shows explicit state, not whole-stack success. Fixture/role/service graphs consume the same envelope reservations before deployment.

## 3. Preview gateway, feedback and evidence passport — 1.0

Preview access passes through an authenticated gateway. Grants bind organization, project/repository, environment, allowed viewer capabilities and expiry; upstream routing uses trusted ownership, not user-supplied URLs. No bearer credential in public GitHub text/query strings. If cross-origin session handoff is needed, exchange a single-use audience-bound short-lived code and set a protected cookie; deny open redirects/CSRF and origin confusion. Guest may see the candidate app but receives no Ghostlight control API or cloud rights.

Gateway displays generation/source and denies expired/destroyed/quarantined access. User-supplied host/custom domain needs DNS ownership/TLS qualification and safe routing. Websocket/SSE/file uploads are capped; unknown candidate response headers cannot weaken gateway security. Preview app's own authentication remains separately exercised by fixtures.

Reviewer room stores resource-authorized threads and findings, generation, optional page/test/request reference, owner and resolved/carried-forward state. Screenshot attachments are scanned/bounded. Candidate update marks prior feedback historical; explicit carry-forward preserves original provenance. Reviewer checklist acceptance never becomes authoritative invariant evidence or production permission.

Evidence passport references signed gate results plus exact identities, topology, fixtures, fault schedule, completeness, confidence, spend and cleanup observation. A mutable dashboard view assembles an immutable manifest/digest; issuing an amended passport creates a new version and links the old. Export contains sanitized authorized evidence, signature/key identity and verification instructions. Retention/permission revocation applies to access; cryptographic signatures cannot retroactively erase already downloaded copies.

## 4. API/CLI, fixtures, reset and clone — 1.5

CLI uses short-lived authenticated device/browser login or scoped service-principal token. Device-flow support depends on qualified IdP; never paste a long-lived owner token into a suggested shell command. API/CLI use console-equivalent permission, entitlement, resource-version and idempotency checks. No native cloud credentials are returned. SDK unknown enum handling and schema compatibility are tested.

Fixture packs carry owner, schema version, source/license, synthetic provenance, seed, checksums, service bounds and redaction/visibility policy. Production snapshots and unreviewed imported datasets are prohibited. Tenant-provided fixtures enter scan/classification and require explicit assurance/qualification; a label “anonymized” is not proof. Synthetic snapshot restore has a bounded artifact size/dependency compatibility and cannot import secrets/native cloud resource identities.

Reset pauses claims, stops tests/faults, creates a new generation, loads approved synthetic state transactionally where possible, reseeds independently and reruns mandatory gates. Failure keeps `degraded/failed` operation state with prior/reset references; never silently declares data clean. Clone creates a new environment/ownership/reservation and fresh identities/secrets; only allowed immutable artifacts/synthetic data transfer, no reused workflow IDs or real integration effects. Original TTL does not grant unlimited clone lifetime.

## 5. Suspension, schedules and admission fairness — 1.5

Lifecycle desired `absent` always overrides scheduling. While desired `present`, add orthogonal `runtime_intent=running|suspended` and observed runtime state; do not confuse suspended with destroyed. Suspension stops independent tests, removes/verifies faults, blocks ingress, drains application claims, revokes short-lived runtime access and stops interruptible compute. Dedicated data volumes/object state may remain only under declared retention/quota; dependency service residual cost stays visible. A profile may destroy synthetic PG/Redis runtime after a verified snapshot, but this is a versioned qualified strategy, not implicit scale-to-zero of durable data.

Schedule changes and suspended/resumed runtime/fixture identity increment generation when the testable configuration changes; previous evidence no longer qualifies the new ready generation. Resume requests current entitlements/capacity, refreshes secrets, restores qualified synthetic data, checks compatibility and runs mandatory gates. It may queue/fail safely. Never set ready before full revalidation. Original `expires_at` remains; waking cannot reset TTL, and expiry during resume switches to teardown. Account restriction can prohibit wake while still allowing destroy/abort.

Schedules specify IANA timezone, weekly intervals, DST handling and bounds. Initial DST rule: nonexistent local wake time moves to next valid instant; repeated time executes once keyed by schedule occurrence. Operator-approved one-off override has expiry, quota and audit. Activity-driven auto-wake is opt-in/rate-limited and authenticated; public health probes cannot create cloud spend.

Queued admissions use bounded per-org/project limits and weighted fair service within profile/capacity pools. Expired/canceled reservations are released exactly once; runnable job aging prevents starvation. Calendar reservations commit resource quantities/time windows transactionally, have lead-time/cancellation rules and never overbook a dedicated experiment pool. Priority affects waiting order, never privilege or budget bypass. Report queue wait/rejections separately from admitted provisioning latency.

## 6. Comparable runs and failure recipes — 1.5

Comparison requires declared compatible profile, topology, fixture/seed, workload, harness/policy version and observation phase. Baseline must be explicitly selected, recent and authorized; source/base mapping alone does not imply equivalent deployment. Run repeated measurements where noise matters, report sample count/confidence/variance and materially changed context. Incomparable or incomplete observations return inconclusive, not a calculated green score. Both original signed outcomes remain unchanged.

Failure recipe records approved immutable ingredients: source/artifacts/config/schema/template/harness, fixture seed, bounded traffic/fault schedule and replay mode. Replay creates fresh environment/generation, credentials, quotas and signed report. External providers/webhooks use stubs unless separately authorized; real-effect calls are not replayed by default. Unknown nondeterministic provider behavior is disclosed. Reproduction failure is a new outcome with differences, not an overwrite of the initial failure.

Policy previews evaluate a proposed action against current catalog/resource/cost/permission state without mutation, showing reasons and potential approvals. Execution reauthorizes and recomputes under locks; stale policy preview cannot authorize a broader action. Approvals bind action digest, organization/project/environment/generation, limits and expiry; new source/profile invalidates approval. No approval may waive cross-tenant isolation or forge invariant success.

## 7. Customer-owned connector — 2.0

Hosted SaaS may orchestrate a qualified connector in the customer's dedicated preview account. SaaS holds a connector-specific identity, not customer admin keys. Customer installs a reviewed signed image/IaC stack; connector verifies account/cluster, org association, workload identity and permissions boundary. First support one account/region topology. Production accounts are excluded by policy and independently verified customer setup; “BYOC” is not permission to broaden fault targets.

Commands are signed, audience/account/org/connector bound, expiration-limited, operation/generation keyed and monotonically sequenced per connector stream. Connector durably stores command IDs/results/high-water mark, rejects replay and checks native resource ownership/local policy before mutation. Each command/action uses the hosted action state machine (`planned -> running -> succeeded | failed | uncertain | canceled`) plus a native target/operation ledger. One native mutation per conflicting resource is serialized; local/database leases fence state writes but never count as fencing a cloud API call. A timeout/crash after a possibly successful mutation records `uncertain`; later create/update/destroy/replacement waits until the prior runner/process is confirmed terminated and native/provider state is observed. Never enqueue a conflicting command solely because a lease expired. Reconciliation records stable action/resource IDs before reporting success. Key rotation has overlap/revocation; a valid old signature cannot override an expired command. Customer inbound/outbound network arrangement must support mTLS/approved outbound polling without opening an arbitrary shell endpoint.

The connector runtime/command ledger runs in a qualified customer management failure domain separate from PR workloads and the target preview cluster. It has durable monotonic sequence/state, reliable multi-zone or equivalent control capacity, independent health/expiry checks and narrow native inventory/cleanup identity. It is never scheduled solely inside the workload cluster whose failure it must clean up. Offline-from-SaaS behavior freezes new admissions/privilege changes; already accepted safe cleanup/expiry intents continue while provider control APIs are reachable. Customer emergency operator path and instructions remain available even if Ghostlight billing/account is restricted.

Cloud tags are inventory metadata, not an expiry service. Each admitted environment/fault registers a bounded trusted expiry/removal action in an independent management control plane with durable retry/alarm; apply operations in that target provider/account are idempotent and observed before retry. Fault catalog admits only types with a proved independently bounded removal path (for example, an external lease-expiring traffic proxy or a qualified out-of-band action). Faults requiring a dead/unreachable target cluster controller to clean up are disabled for this connector until separately qualified. A full target-cluster loss can prevent verifying native resource absence, and a provider API/region outage can delay removal despite durable alarms. In those cases mark `cleanup_unresolved`, quarantine, inhibit new experiments, notify the named customer operator and retain resource IDs until independent inventory proves absence. Never promise fixed cleanup completion during a control-plane outage.

Test connector/watchdog/process/node/target-cluster failure, clock skew, provider API outage, replay/high-water recovery, delayed native success, and conflicting destroy/update. Signed commands do not fence an in-flight provider call; serialization, stable IDs and observe-before-retry provide that safety.

Disconnect/revoke stops admissions, revokes grants and requires customer/native inventory cleanup receipt. If access is lost, mark unresolved and provide exact resource IDs/operator actions; never pretend deleted. Customer cloud bill and Ghostlight subscription are separate views/obligations. Connector upgrades preserve the previous supported cleanup runtime until all older resources are removed.

## 8. Fleet policy, drift and reliability programs — 2.0

Policies are immutable versioned bounded declarative rules (qualified OPA/Rego or equivalent), with schema, test fixtures, resource/time limit and publication approval. Decision input uses trusted inventory/identity/quotas; PR labels do not confer authority. Exceptions carry explicit scope/reason/approver/expiry, cannot be self-approved for expanded privilege and remain labeled exceptions. Policy revocation affects new actions and a reviewed response for running resources, not retroactive invented pass states.

Drift compares declared and provider-observed identities/configurations and classifies compatible, unauthorized, absent or unknown. Observe first; unknown ownership forbids automatic deletion. Default remediation is a reviewed plan, serialized by existing native locks; auto-repair only for explicitly cataloged low-risk operations after qualification. Candidate-built “observations” are not authoritative provider inventory.

Coverage scorecards group declared service/dependency invariants with weights, required test profile and evidence max age. Proposed coverage score = passed-fresh applicable weights / total applicable required weights, reported with failed, untested, stale and inconclusive components. It measures evidence coverage, not outage probability or production SLA. A service may have a high fraction and still be blocked by a failed critical invariant; policy enforces that separately. Methodology/version and actual test dates are visible.

Campaigns schedule approved target sets/window/profile with dedicated capacity and per-run abort thresholds. Reauthorize every run against current ownership/generation and missing-watchdog state. Source/fixture/policy changes cancel or reschedule safely. Campaign abort removes every recorded/native discovered fault and verifies recovery; failed removal quarantines resources. Remediation task links to immutable failure and owner/due date; passing rerun resolves a finding with preserved history.

## 9. SaaS persistence, economics and long-term compatibility

Organization and billing state follow the foundation. All experiment/preview schedules, clone/reset/API/CLI and connector admission paths check current entitlements. Subscription restriction cannot prevent emergency abort, export, verified teardown or native cost stop. Inventory/evidence/audit retention uses bounded profiles and legal holds; raw Terraform state is restricted operator material even after account closure.

Expanded objects include projects/grants, installation intents, catalog/template versions, fixtures, preview grants, feedback, schedules/runtime intentions, admission queue/reservations, baseline comparisons, replay recipes, connectors/commands/receipts, policy versions/approvals, drift findings, coverage policies/snapshots, campaigns and remediation tasks. Organization FKs, role separation, immutable provenance, ledger uniqueness and generation checking apply throughout. New capabilities require independent fleet/restore/cost/privacy qualification rather than inheriting the initial 20-preview claim by assumption.
