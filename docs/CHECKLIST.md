Evidence: `internal/{environments,actions,provider,costmodel,catalog,recipe,postgres}`, `catalog/` (embedded), `migrations/` — schema verified against real PostgreSQL. **Catalog validation implemented as a set, not a file at a time** (`internal/catalog`, 11 tests), because most catalog-wide defects are invisible to per-file validation: two files claiming one recipe name are each individually runnable and the platform still cannot tell which one a caller meant. Per-recipe validation stays in `internal/recipe`; this package adds only set-level defects, so there is one implementation of "is this recipe valid" rather than a looser second opinion. **The catalog is embedded in the binary** (`catalog/embed.go`) rather than read from a path, so a compiled binary cannot be missing a recipe and a candidate cannot silently run against nothing; files stay on disk so they remain reviewable diffs. **Remaining, and not claimable here:** the HTTP API surface and its authentication middleware, and the price-list loader.

- [x] G0.5 **[DONE]** Create least-privilege identities for controller, build, allocator, runner, runtime, experiment, janitor and signer. Closed via #120 at merge by owner. Evidence: `internal/roles` (16 tests). Least privilege is a **matrix, not a motto**: 8 roles × 15 actions, every cell decided, no implicit defaults — a matrix with implicit defaults is one nobody can review. The load-bearing denials are written as data: build cannot provision, sign, touch secrets, write the ledger, write evidence, serve traffic, revoke, quarantine, inject faults or destroy (the G0 gate, pinned as a test and re-proved independently in `test/gate` g0 suite); build **reads** the ledger and observes provider state read-only, which is a correction to the earlier claim here that it cannot touch the ledger at all - `internal/roles` pins that grant as required for the build to do its job, and read-only access is not one of the three credentials; runners mutate and destroy but cannot sign, since a runner that could sign its own evidence could fake a pass; the runtime serves and reads its scoped credential but writes nothing, since a workload that could write evidence could qualify itself; the janitor retries teardown and quarantines but cannot provision, since it could otherwise manufacture what it discovers; the signer signs and reads, nothing else, since broader rights make it a confused deputy; the controller decides but never provisions, mutates, or destroys, since that would bypass the ledger and its fencing; experiments inject faults but cannot rebuild, since a fault that rebuilds is an outage with a costume on; allocators provision but never destroy, since destruction goes through verified cleanup. Creators write credentials, consumers only read — a role doing both could rotate a credential out from under its own workload unnoticed. Unknown roles and unknown actions **deny**: a typo must fail closed, not open a hole shaped exactly like the typo. Every action is held by someone (no dead policy — the tests caught two) and denied to someone (no boundary-less action), and no role does everything (no superuser, or every other row is decorative). Each decision carries a reason, because a denial nobody understands becomes a ticket for broader rights, and broader rights to stop the tickets is how least privilege dies. **Remaining, and not claimable here:** binding these identities to cloud IAM roles and the contract fixtures in G0.6.

- [x] G1.4 **[DONE]** Implement quotas/TTL reservations and extension/destroy authorization. **Covers G-F06.** Evidence: `internal/quota` (23), `internal/admission` (17), `internal/ttlwatch` (15), migration 0001 `capacity_reservations` — 61 tests. Admission reserves repository/actor/fleet concurrency, CPU/storage ceilings and monetary allowance **transactionally across all four scopes at once** — validate-then-insert is the race SPEC.md warns about, so every scope is checked before any is consumed and a refusal leaves nothing held. Twenty-four concurrent controllers against one slot admit exactly one; a concurrent-admission test proves the fleet never oversubscribes. Partial reservations cannot occur, because they leak capacity no environment accounts for. A reservation must name its environment, and a scope with no grant is refused rather than treated as unlimited. Expired windows grant nothing. Release is idempotent, because a retried cleanup must not credit a slot twice and invent capacity nobody paid for. TTL defaults to 24h and clamps to the 72h maximum rather than refusing, since a caller asking for too long should get the policy maximum but never the extra time. It is now an explicit membership test, with the reasoning recorded so the clever version is not reintroduced. The other three: a versionless recipe validated despite the row's own "a reproduction of a different build is an anecdote"; an observer outage was reported as a replayed failure; and merge silently dropped a conflicting finding.
- [x] G8.9 **[DONE]** Qualify Slack/Teams/Jira notice/finding connectors with redaction and scoped identity; G-F24. Evidence: `internal/connector` (27 tests). A connector is the one place where Ghostlight's data leaves this system and arrives somewhere the customer did not fully control, so three properties each have a wrong obvious implementation. **Redaction is fail-closed**: a field is sent raw only if the policy names it explicitly and anything not named is redacted, because redacting "the fields we know are sensitive" means sending everything else and the field nobody thought of — in the notice format nobody read — is exactly how a credential reaches a channel. A name allowlist is **not a licence to leak**: an allowlisted field whose value matches a secret pattern is still redacted, because the allowlist says which fields may be *sent*, not that their contents are safe. Free text is the most likely place to leak and is redacted by default, with the policy having to opt in, and even allowed free text is pattern-checked. **Scoped identity is one-to-one in both directions and cannot be quietly re-pointed**: an external identity already bound elsewhere is refused, a scope with two identities is refused, and rebinding the same identity to the same place is idempotent — because a re-pointed identity is indistinguishable from a hijacked one at the far end, and a notice is written for one audience. **Signed callbacks** bind the connector, timestamp, nonce and body in the signed material, so none can be borrowed from another callback; the timestamp is checked before the signature so a stale or future callback is refused as a clock problem rather than an attack, both directions are refused, and a replayed nonce is refused and remembered, because a signature that verifies forever is a permanent credential. **Nothing that leaves carries a connector secret**: delivery checks the redacted payload against the connector's own secret before sending, so a secret that got into a field by accident is caught at the boundary rather than in somebody's channel. **Remaining, and not claimable here:** the transport to each provider, the OAuth installation flow, and the signed callback verification against Slack's and Jira's real request formats.

- [x] G9.4 **[DONE]** Implement bounded versioned policy tests/publication/approvals and visible expiring exceptions; G-F27. Evidence: `internal/policypublish` (21 tests). Publishing a clean suite is unglamorous; the row is about the path where someone must ship with a test that does not pass, which is legitimate during an incident or a compatibility window and illegitimate if done quietly or forever. **An exception must expire**: `ExpiresAt` is mandatory, must be after `GrantedAt`, and is bounded by `MaxExceptionTTL`, because a permanent exception is a deleted test and granting one should not be possible without that being visible as a decision. **An exception must be visible**: every exception ever granted stays attached to its publication forever and `StatusOf` lists all of them, expired ones included — and a policy whose only exceptions have lapsed still does not report `Clean`, because its history is part of the record, so there is no way to read the policy as clean while the waiver sits elsewhere. **It must be granted by somebody other than the approver of the release** (`ErrSelfException`): nobody waives the policy they are releasing, and the single-person version of that check is a rubber stamp wearing a checkbox. **It does not carry forward**: an exception binds to one version number, `Supersede` requires a higher number and starts the new publication with zero exceptions, and re-publishing a failing suite on the strength of the previous version's waiver is refused — a waiver is a judgement about one set of tests at one moment, and inheriting it means the next release ships a failure nobody re-examined. **An expired exception suppresses nothing**, and the refusal says so (`ErrExceptionExpired`) rather than a bare failure, because the honest answer to "why will this not publish" is usually "because the waiver lapsed" and not saying it sends people looking in the wrong place. Suites are **bounded and refused rather than truncated** (`MaxTests`, `MaxSuiteDuration`, with exactly-at-the-bound accepted), versions are **digested** so results are granted against a specific set of checks, and `Verify` detects a published version whose tests were mutated after the fact. **Untested is not passing**: results must cover every test exactly once, a missing result is refused rather than treated as a pass, and failures come back in deterministic order.
- [x] G9.5 **[DONE]** Build native drift detection/ownership classification and reviewed serialized remediation plans; G-F28. Evidence: `internal/drift` (29 tests, 44 cases). Classification is **fail-closed**: an object whose tag key is a near-miss of the ownership key — after folding case and `- _ . / :` separators, so `ghostlight_env` for `ghostlight-env` — is `ClassUnknown`, **not** `ClassOwned`, and a test asserts exactly that, because a near-miss tag that parsed as ownership is how something that is not ours gets deleted. An empty or whitespace-only tag VALUE is `Unknown` too, never Owned and never Orphaned: an empty tag on a resource we did not create is worse than none, because it looks like an answer. Untagged objects with a known type are `Unmanaged` (the customer's own, never deletable) and unknown types are `Foreign`. Remediation is where a classification mistake becomes a deletion, so: **`Remove` is planned only for orphaned objects and only when removal is explicitly allowed** — a test asserts a plan built without that option contains zero remove steps even when every finding is orphaned, and that unmanaged and foreign objects never produce a remove step under any options. Every plan step is reviewable: approval requires a **named reviewer**, an unreviewed plan cannot execute, and an executed plan cannot execute again, because two operators running one remediation concurrently is how a remove step races a tag step. Plans are **bounded rather than truncated** (a truncated remediation plan that looks complete silently leaves half the drift behind) and **deterministic**, verified by shuffling the findings several ways and comparing byte-identical plans. `ActionTag` is defined but deliberately never emitted: tagging an unproven resource manufactures ownership.
- [x] G9.6 **[DONE]** Build service owners/dependency coverage, fresh/unknown/stale methodology and scorecards; G-F29. Evidence: `internal/coverage` (26 tests). The product spec fixes the formula and this implements it literally: **score = passed-fresh applicable required weights / total applicable required weights**, and every term in that sentence is load-bearing. The denominator counts every applicable required weight while the numerator counts only the ones that passed fresh, so **an untested or unknown invariant drags the score down rather than being neutral** — a service can never look covered on the strength of tests that were never run, and untested, stale and inconclusive each get their own reported component so a reader sees not just how good the number is but why. **The checks are ordered**: a result from the wrong profile is inconclusive whether it is ten seconds old or ten years old, and freshness is judged before the outcome, so **a stale failure is stale and not failed** — it proves what was true once, and it must not veto a service on the strength of a result nobody has refreshed. A future-dated result is refused outright, because a skewed clock that certifies freshness is worse than no clock. **The score and the blocked state are reported separately, and that separation is the point**: a service may hold a 95% coverage fraction and still be blocked by one failed critical invariant, because coverage says the evidence exists and says nothing about whether the evidence is good. A critical invariant that is untested, stale or inconclusive does not block — nothing has been shown broken — but it is listed as an unverified critical so that "not blocked" is not read as "fine". **Advisory invariants are reported but do not move the score**, and a service with no applicable required invariant is reported as having *no coverage*, which is a different fact from covering nothing. Scope, owners, the methodology version and the **actual test dates** behind every number are all visible, and a report that cannot be checked is a number nobody can argue with — which is the problem with a number nobody can argue with. Dependencies get their own coverage view across the services that declare invariants about them.
- [x] G9.7 **[DONE]** Implement scheduled approved campaigns/game days, per-run reauthorization/abort and immutable remediation task history; G-F30. Evidence: `internal/campaigns` (28 tests). The row's hard part is that **an approval is a record, not a capability**, so `Start` reauthorizes EVERY step immediately before that step executes rather than once at the top of the run, and the call order is asserted as campaign/actor/step. The case the design exists for is tested: **authority revoked between step one and step two stops the run mid-way**, with step three unexecuted, the reason recorded, and the steps that already ran returned as facts rather than discarded — throwing them away would make the record wrong. **An undecidable authorization is surfaced as itself and never as `ErrNotAuthorized`**, because an outage reported as a policy decline is a lie an operator will act on; the run still stops, since "we could not ask" is not "we were told yes". `Start` requires a reauthorizer, so the package will not run a destructive exercise on the strength of an approval it already holds. **Abort is available from any point and refuses only for a missing reason, an already-aborted run and a closed run** — a destructive remedy with no stated reason cannot later be told apart from an outage, and a second reason would overwrite the first, which is the one that explains what was done; an out-of-band `AbortRequested` stops the next run before anything executes or is reauthorized. **The window is re-checked at start, not only at approval**, because running a closed exercise late means running it against a fleet nobody agreed to be watching. **The record is immutable**: `Record` is the only path a result takes into a run, so the rules cannot be bypassed by writing to `Results`; a closed run accepts nothing and a step's result can never be overwritten, because a remediation task history that can be edited after the fact is a story about what might have happened. Step identifiers are unique and bounded (`MaxSteps` at approval, refusing a game day that is really a scheduled outage), and `Summary` sorts by step so a record can be diffed. **Remaining, and not claimable here:** the scheduler that triggers campaigns, and the execution backends the steps call.
- [x] G9.8 **[DONE]** Qualify SIEM/evidence export/signature rotation, retention/hold and closure; G-F31. Evidence: `internal/evidenceexport` (32 tests). Four traps, each with a wrong obvious answer. **Signing survives rotation**: a signature records the key and the moment it was made, and verification asks only whether that key was valid *then* — so a key that has since rotated out or expired does not invalidate what it signed. Demanding the signing key be current would reject the oldest records in the archive, which are exactly the records an investigation wants, and rotation therefore retroactively invalidates nothing. Rotation itself is refused while the successor is already valid, because two keys valid at once makes "which key signed this" a question with two answers. **Holds are evaluated at the moment of deletion, not cached when applied**: a hold placed *after* a retention deadline arrived still suspends the sweep, because a regulatory investigation arriving after the data would have been deleted is the normal case and not the exception, and a hold released a moment before the sweep runs no longer suspends it. **A sweep is refused whole** if any candidate is held, rather than deleting the eligible records and skipping the held one — a partially applied sweep leaves the archive in a state nobody can describe, and an archive in an indescribable state cannot be audited. **Releasing a hold destroys nothing**: the record survives and a later sweep collects it, because a release that also expunged the evidence would be a release with an ulterior motive wearing a legitimate costume. **Closure releases neither evidence nor holds**, because an investigation outlives the company it was launched against; a closed account's evidence is still evidence and is still exportable, digest-bound and signed. Exports are manifests rather than blobs, scoped to one tenant and deterministic, so a customer can check what they received against what existed, and a bounded export is refused rather than truncated — a truncated export that looks complete silently omits the record nobody was looking for.
